    How to read this — plain-language guide

    This app runs sandboxed, but it can still call many services and devices. Each call lands in handler code that may or may not re-check who is calling. This page sorts those calls by how well they're defended:

      The colored words above are the plain-language labels used throughout the page; the smaller grey word in brackets is the exact technical term (for anyone cross-referencing AOSP/SELinux docs).

      Lower-level targets this app can reach that aren't Java system services: native daemons (C/C++ servers reached over Binder or a socket), hardware services (HALs), and direct device-driver access. We inspect each server's compiled code for a caller check. Grouped below by what we found — the open and couldn't-locate groups are where to look first.

      The blast radius: if this subject is compromised, where can it go next? Becomes = it can run code as another domain with no further bug (an exec transition, or writing a file that domain loads as code). Can attack = it can feed input into another domain's code, so a bug there would escalate. Each target is resolved to the on-disk code to open, and to the single policy rule whose removal cuts the edge.

      The complete list of what this app can reach, grouped by kind of object (files, sockets, services, devices…). The bar shows, per kind, whether there's a second permission check in the code behind the object. Most files/devices are governed by the sandbox policy alone; only services and sockets have handler code that can add a check.
